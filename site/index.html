Why not just axe DevTools?

Same engine. Completely different answer.

A browser extension tells you a CSS selector is wrong. Content authors cannot act on that. The scanner translates every finding into Liferay terms, audits what the browser cannot see, and remembers the results.

Product tour

Built into the place where pages are made

One button next to the viewport switches in the page editor. A drawer the size of the configuration panel. Three tabs: Draft, Published, Site.

Draft tab: live feedback while you author

Scan the page you are editing. Findings are grouped by rule, with a compact impact sticker, the WCAG criterion, and the fragment and editable they belong to. Highlight the element on the canvas or select it to open its configuration.

  • Grouped by rule, filterable by impact, each with a link to the rule documentation.
  • One-line element summary instead of raw HTML: tag, alt, href, role and the attributes that matter.
  • Page-level content checks folded in: translations, image alt text, style book contrast.

Published tab: audit what visitors actually get

The editor DOM is not the page. It adds classes, hides content from assistive technology and renders toppers over your fragments. The Published tab loads the public URL in a hidden frame, runs the same scanner there and maps the results back to your draft fragments.

  • Same origin, same session, no copies of your content leave the portal.
  • Findings mapped by layout item id, so you still jump to the right fragment in the editor.

Site tab: the whole site, as an anonymous visitor

Every public and private page is fetched without credentials and audited in your browser, light and dark when the theme defines a dark scheme. Results go to site-scoped Objects with a score per page, so the next scan shows the delta.

  • Theme-aware color schemes. The dark pass only runs on pages whose theme actually defines one.
  • Theme and style book recorded per page, so design issues are attributed to the design.
  • Progress, cancel and a stale-scan notice after 14 days without scanning.

Report fragment

A report anyone on the team can read

Drop the Accessibility Report fragment on any page of the site. It reads the scans from the Objects and renders score, issues by impact, trend, pages, rules, fragments, themes and style books. Switch between light and dark results. Responsive, Clay-styled, no extra CSS framework.

Liferay-aware rules

Nine rules axe will never ship

They run as custom axe rules under the liferay tag, next to the standard WCAG ruleset, and catch the mistakes that happen specifically when pages are assembled from fragments.

liferay-placeholder-text

Placeholder text left in the page

"Heading Example", "Go Somewhere", card samples: the fragment defaults nobody changed.

WCAG 1.3.1 · serious
liferay-link-destination

Link without destination

Link and button fragments published with no URL configured.

WCAG 2.4.4 · serious
liferay-single-h1

Multiple h1 headings

Stacked heading fragments that all render as h1, breaking the page outline.

WCAG 1.3.1 · moderate
liferay-generic-link-text

Generic link or button text

"Read more", "Click here", "Learn more" without context for screen reader users.

WCAG 2.4.4 · serious
liferay-duplicate-link-text

Same text, different destinations

Links that read the same but go to different places, typical in card grids.

WCAG 2.4.4 · moderate
liferay-new-tab-warning

New tab without warning

Links that open a new tab with no visible or accessible indication.

WCAG 3.2.5 · minor
liferay-alt-filename

Alt text is a file name

Images whose alternative text is "photo_1234.jpg", the default from the upload.

WCAG 1.1.1 · serious
liferay-video-captions

Video without captions

Embedded and external videos with no caption track to review.

WCAG 1.2.2 · needs review
liferay-carousel-autoplay

Carousel that autoplays

Sliders moving on their own without a pause control.

WCAG 2.2.2 · serious

Five content checks through Liferay's APIs

  • Missing translationsTexts not translated into every language the site offers.
  • Image alt unsetImage fragments with no alternative text in the page definition.
  • Library images without descriptionDocuments and Media images in the site and the Global site.
  • Style book token contrastBody, primary and secondary colors read from the applied style book.
  • Page titlesEmpty or duplicated titles across the site's pages.

How it works

One zip. No servers. Works on every site.

Everything runs in the author's browser with the author's session. The Objects are site-scoped, so each site keeps its own scans and permissions.

  1. Deploy the client extension

    Drop the zip in your Liferay deploy folder or install it from Marketplace. It brings a global JavaScript and the Accessibility Scan, Page and Finding Objects.

  2. Open any page in the editor

    A tiny loader runs on every page and only fetches the scanner when the editor is open. Press the new toolbar button and scan the draft or the published page.

  3. Scan the site, read the report

    Run a site scan from the Site tab, then place the Accessibility Report fragment on a page for the team. Rescan whenever you publish.

Global JavaScript

The editor panel, the scanner (axe-core and the Liferay rules), the published and site scanners. Clay classes only, served by the portal.

Objects (batch)

Accessibility Scan, Page and Finding, scoped per site, with English and Spanish labels and REST endpoints out of the box.

Report fragment

An importable fragment collection with the configurable Accessibility Report: trend length, pages to list, sections to show.

Questions

Good to know

Does any content leave my portal?

No. Pages are fetched by your browser from your own portal, audited there and stored in your own Objects. There is no external service and no telemetry.

Who can see the report?

Whoever has permission to read the Accessibility Scan Objects on that site. The fragment uses the visitor's session, so a visitor without permission sees a sign-in hint, not the data.

Which Liferay versions?

Liferay DXP quarterly releases with client extensions, Objects and the page editor. The exact tested versions are listed on the Marketplace page and in the repository.

Is a site scan slow?

About two to four seconds per page and color scheme, in your browser. Keep the tab visible while it runs: browsers throttle background tabs and axe depends on timers.

Does it replace a manual audit?

No tool does. Automated checks find a share of WCAG failures; findings marked "needs review" tell you where a person has to look. The scanner makes that person's work shorter and better targeted.

Make accessibility part of publishing

Install the extension, open the editor and scan. Your authors will know what to fix before anyone else finds it.
